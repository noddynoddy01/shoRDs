# 12. Fine-tuning feasibility

Date 2026-11-04 · **Status: PROPOSED (analysis only). Nothing was trained, no dataset was downloaded or built, no GPU was rented. Cost: $0.00. No large training run should start until the five gates in section 7.4 are met.**

## 7.1 Should we fine-tune at all?

Not yet. The order of leverage, cheapest first, is: (1) prompts and the retrieval/anchoring structure that already exist, (2) a better document extractor, (3) choosing a stronger base model, (4) fine-tuning. Fine-tuning is worth considering only if the evaluation (`05_…`) shows a **specific, repeatable** failure that stages 1 to 3 do not fix and that training data can address (for example: the model writes fluent text but does not copy numbers exactly; or it ignores the "unavailable" instruction). Without that evidence a fine-tune is a cost with no target.

## 7.2 Options

| Method | What it changes | Memory (rough, per vendor/community guidance, not measured here) | When it makes sense |
|---|---|---|---|
| Prompting / few-shot | nothing trained | none | first resort; already used |
| LoRA (low-rank adapters) | small adapter on a frozen base model; the base is kept | a 27B-class model in BF16 needs tens of GB for weights plus activations; one 80 GB GPU is the usual floor | consistent formatting, field-extraction accuracy, tone |
| QLoRA (adapters on a 4-bit base) | same, with a quantised base | roughly a quarter of the weight memory; a 24 GB GPU can hold a 20B-class model, a 27B-class is tight | when the GPU is small; accuracy slightly below full-precision adapters in the literature (◇ background knowledge) |
| Full fine-tune | all weights | several times the model memory | not justified at this scale |
| Distillation from a stronger model | train a small model on a larger one's outputs | as LoRA | **only where the larger model's terms of use permit it. Claude outputs are NOT used (see 7.3)** |
| Train a small checker (MiniCheck-style) | a 400M to 800M model that judges "is this statement supported by this passage" | fits a consumer GPU | the most promising targeted use: it would strengthen Stage E beyond lexical checks. The MiniCheck paper (verified abstract) reports a 770M checker approaching GPT-4 accuracy at ~400x lower cost; its training data were synthesised by GPT-4, which is a licensing question for us (7.3) |

Both `gpt-oss-120b` (vendor page: fine-tunable on a single H100 node) and `gpt-oss-20b` are documented as fine-tunable. Qwen and Gemma are widely fine-tuned with community tooling; I did not verify tooling versions.

## 7.3 Data: what is allowed, what is not

| Source | Use | Licence position (primary source) | Verdict |
|---|---|---|---|
| **Claude outputs** (briefs from production or from the benchmark) | train the native model | Not scraped, not used. Anthropic's terms restrict using outputs to train competing models, and the instruction in this phase is explicit. I did not read the current commercial terms for this phase; the owner/counsel should confirm | **NO** |
| SciRIFF (Allen AI; 137K instruction instances over 54 scientific tasks) | instruction tuning for extraction/summarisation tasks | Dataset card fetched this phase: licence field `odc-by`, with per-subset licences; **three source datasets are CC BY-NC (MultiCite, SciFact, SciReviewGen)**, so a commercial model must exclude those subsets. The card says nothing about restrictions arising from model-generated parts, so that needs checking before use | **Possible, with subset filtering and a check of the card's remaining caveats** |
| Open-access papers with a CC BY (or CC0) licence, e.g. a PubMed Central OA commercial-use subset | source text for building our own instruction pairs | licence is per paper; each paper's licence must be recorded (the Phase 4 `selection_record.csv` already does this). Papers with NC, ND or no licence are excluded | **Possible, per-paper** |
| Human-written reference summaries made by shoRDs raters | training targets | rater agreement and ownership terms must be written down first; the benchmark papers used for **evaluation** must never be used for training (see gate 3) | **Possible, small** |
| Synthetic pairs generated by an open-weight model whose licence allows it (Apache-2.0 models: Qwen3.8, gpt-oss, Gemma 4, Mistral Small 4) | bootstrapping, then filtered by the claim guard and by humans | Apache 2.0 places no restriction on using outputs; I read model-licence summaries, not the full texts | **Possible**; the Llama 4 community licence has derivative-naming and attribution terms and is the least convenient |
| Restricted papers (no or unknown licence) | any training or evaluation | `licensePolicy` forbids | **NO** |

## 7.4 Gates before any training run (all must hold)

1. **Objective written down:** which failure, measured how, target threshold.
2. **Baseline measured:** the un-tuned model's scores on the evaluation (`05_…`), so that an improvement is real.
3. **Evaluation set frozen and disjoint:** the 50 benchmark papers never enter training data. Dedupe by DOI and content hash; the content hash already exists in the pipeline (`contentHash`).
4. **Dataset built with recorded provenance:** for every training item, source, licence, who or what wrote the target, and the date. Rejected items kept with the reason.
5. **Cost estimate and reproducible pipeline approved by the owner:** exact GPU type, hours, price, seed, library versions, and a script that regenerates the adapter from the data. No spend before approval.

## 7.5 Order of work if the gates open

1. A small **supported-by-evidence checker** (Stage E) trained on public NLI/fact-checking-style data with permissive licences plus our own guard-labelled negatives: cheapest, most useful, runs on a small GPU.
2. LoRA on the extraction stage (Stage B), where outputs are short, structured and verifiable by the existing anchor check (each item must quote its chunk). Failures are self-labelling, which makes good negative examples.
3. Only then consider tuning the brief-writing stage.

## 7.6 Cost placeholder

A single LoRA run on a 20B to 30B-class model with a dataset of a few thousand items is, by general experience (◇), a matter of hours on one 80 GB GPU: at $2.89/h (third-party listing) that is tens of dollars per run, not thousands. Dataset construction and rater time dominate. This is an order-of-magnitude statement, not an estimate; the real one is gate 5.

## 7.7 What exists in the repository already

`backend/finetune_model.py` is pre-existing scaffolding (read this phase): a QLoRA script for `Qwen2-VL-7B-Instruct` that, **if `papers_dataset.json` is missing, silently writes and trains on one hard-coded invented sample** (a ResNet record with a made-up label) for 3 epochs. It has no held-out set, no evaluation, no licence record, truncates at 512 tokens, and pads labels (so padding tokens are trained on). It is not referenced by any JS, Docker or CI file I could find. It is **not used, not trusted and not a starting point**; running it would produce an adapter that looks real and means nothing. Similarly `backend/multi_agent_engine.py` returns hard-coded "analysis" (invented research questions, a "p < 0.001" statistic) for whatever text it is given. See `08_…` for the risk and a proposed (owner-decided) action: quarantine, do not delete.
